# 注释规范

适用于 DeepDeep Word（`dpdp-word`）的源码、测试与 CSS。优先靠可读命名说明意图，而不是用注释旁白。

## 规则

1. **禁止 what 注释。** 标识符、类型或结构已经能说明「在做什么」时，删掉注释。
2. **只留短 why。** 原因不明显时才写：产品规则、算法特殊点、脏数据 / 兼容兜底；通常一行，偶尔两行。
3. **禁止文件头长文。** 模块职责写在 [`docs/`](./README.md)，不要在源码顶上贴会过期的多段概述。
4. **禁止过期考古。** 注释与 CSS 横幅里不要提已删除的 Phase、契约、「v1 时代」等历史。
5. **语言。** 代码注释优先英文。同一注释块内不要中英混杂，除非在引用用户文案 key。

## 允许

- 名字表达不了的产品不变量（例：互译 `poor` 必须先确认再 Next；掌握判定窗口是连续答对）。
- 兼容说明（例：缺 `roundId` 的旧作答归入 legacy 桶）。
- CSS：仅允许极短分区横幅；品牌用词为 **DeepDeep Word**。

## 禁止

- 复述已经命名清楚的 props / 参数 / 返回值。
- 只起装饰作用的 TypeScript 分割线（`/* ---- Section ---- */`）。
- import 上方的长篇「Overview / Responsibilities / Flow」头。
- 重复 CHANGELOG 或 PR 历史的注释。

## 测试

- 测试文件放在 [`test/`](../test/)（见 [coding-standards.md](./coding-standards.md)）。
- 优先用清楚的 `it('…')` 标题，而不是用注释解释断言。
- fixture / 辅助函数默认不写注释，除非编码了非直观规则。

## 合入前自检

- [ ] 没有只是复述下一行代码的注释
- [ ] 留下的注释回答的是 *why*
- [ ] `src/` 与 `test/` 中无 Phase / 契约 / 旧时代考古叙述
